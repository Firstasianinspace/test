## 3. Производительность

**Бандл:** один чанк 677 КБ (195 КБ gzip) + CSS 3,6 КБ gzip. Собственный код — 1,7 % (47 КБ исходников из 2,7 МБ); остальное — библиотеки: react-dom 23 %, Supabase (auth/storage/realtime/postgrest) ~29 %, react-router 13 %, zod 13 %, react-hook-form 5,5 %, TanStack Query 5,4 %.

Что можно сделать и почему не сделано:

- `@supabase/supabase-js` тянет storage и realtime, которые приложение не использует (~14 % исходников). Можно перейти на `postgrest-js` + `auth-js` напрямую — ориентировочно −40…50 КБ gzip, но это ручная сборка клиента и риск для безопасности сессий. Для тестового задания невыгодно.
- `zod` → `zod/mini` ориентировочно −25…30 КБ gzip; низкий риск, отложено.
- Разделение страниц по маршрутам (`React.lazy`) выигрыша почти не даст: страницы — менее 2 % кода.
- Вынос вендорных чанков улучшит кэширование между деплоями, но не первую загрузку.

**Критический путь рендера:** нет веб-шрифтов и внешних CSS; один скрипт и один CSS-файл. Добавлен `preconnect` к Supabase, чтобы рукопожатие TLS шло параллельно загрузке бандла. Удалено 5 неиспользуемых зависимостей (размер бандла не изменился — они не импортировались).

**Реактивность:** запросы TanStack Query ключуются по id и дедуплицируются; списки малы, поэтому виртуализация и пагинация не нужны (сервер ограничивает ответ 1000 строк — **пагинации нет**, это ограничение). Управляемые поля формы перерисовывают страницу на каждый символ — на таких размерах незаметно.

**Утечки памяти:** на живом сайте прогнано 100 циклов «список → объект → задача → назад»: куча колеблется 9,3–10,1 МБ (пила сборщика мусора, роста нет), число DOM-узлов постоянно (44–46), самый долгий цикл 110 мс. В приложении нет подписок, таймеров и обработчиков вне жизненного цикла React.
